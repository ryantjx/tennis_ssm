# Site and Pipeline Audit — 18 October 2026

Scope: the deployed GitHub Pages site, the daily prediction workflow, and
repository hygiene for `ryantjx/tennis_ssm`.

## Summary

The model itself was healthy. The failure was entirely in data acquisition and
in the absence of any signal that acquisition had broken.

From 25 August 2026 to 17 October 2026 the scheduled generation workflow failed
on all 52 consecutive daily runs. The deployed site continued to return HTTP 200
and render normally, serving the 24 August 2026 snapshot. No alert of any kind
was raised: the only visible symptom was a stale date in the page header.

The upstream data host, `tennis-data.co.uk`, made two breaking changes:

1. It moved to HTTPS and began serving seasonal workbooks from a rotating hashed
   directory (`/<hash>/<year>w/<year>.xlsx`), so the hard-coded yearly path
   returned 301 then 404.
2. It began rejecting the default `Python-urllib` user agent with HTTP 403.

The loader retried three times per season, which cannot help against a
deterministic rejection, so every season failed and the run aborted with
`No data could be downloaded`.

## Observed state before remediation

| Signal | Deployed site | Local repaired run |
|---|---|---|
| Latest model run | Mon 24 Aug 2026 | 18 Oct 2026 |
| Eval matches correct | 1324 / 2150 | 1689 / 2740 |
| WTA fixtures matched | 54 of 69 | 5 of 5 |
| Model state as of | 2026-08-24 | 2026-10-17 |

The site was therefore functioning correctly as a renderer while displaying
eight-week-old forecasts. Because the frontend fetches `outputs/latest/*.json`
directly from `raw.githubusercontent.com` at runtime, a stale snapshot is
indistinguishable from a current one without inspecting `generated_at`.

## Root causes

1. **Upstream contract change.** Unpinned external URL structure; no discovery
   step. Failure was deterministic, so retries masked nothing and fixed nothing.
2. **No test gate.** Both workflows built or generated without running tests.
   The Python suite contained no test for workbook acquisition at the time.
3. **No failure notification.** No `if: failure()` step, webhook, or issue
   creation. Consecutive failures were reported only in the Actions UI.
4. **Validation measured shape, not recency.** `validate_predictions_payload`
   confirmed required keys, metric ranges, and unique fixture IDs. An eight-week
   old payload satisfies every one of those checks.
5. **Failures were swallowed as warnings.** The completed-results, fixture, and
   Polymarket loaders each catch exceptions, record an `error` field, and return
   success. A run could therefore be green while producing no fixtures.
6. **No staleness signal in the UI.** The header rendered `generated_at` but
   nothing compared it against the current date.

## Remediation applied

### Data acquisition (`src/data/data.py`)

- Workbook links are discovered from the index page at
  `https://tennis-data.co.uk/data.php`, so the rotating path is resolved at run
  time rather than hard-coded.
- Requests carry browser-like `User-Agent` and `Accept` headers.
- The legacy URL template remains as a fallback if discovery fails.
- Workbooks are cached under `local_data/raw/`. Past seasons are treated as
  immutable; the current season refreshes after
  `TENNIS_DATA_CACHE_TTL_HOURS` (default 6). If the host is unreachable, a cached
  workbook is used so a transient outage degrades to slightly older data instead
  of a failed run.
- The workflow caches `local_data/raw` between runs.

### Pipeline (`main.py`)

- `compute_data_freshness` records `as_of`, `age_days`, `threshold_days`,
  `stale`, and a list of `warnings` in every payload.
- `validate_predictions_payload` requires the freshness block structurally, and
  staleness is reported as a warning rather than an exception. Blocking on
  staleness would hide the last known-good forecast from the site.
- `prune_daily_snapshots` retains 30 days of dated snapshots
  (`TENNIS_DAILY_RETENTION_DAYS`). Snapshots grew by roughly 3 MB per day; 46
  had accumulated, about 111 MB uncompressed, with no retention policy.

### Automation

- `generate-predictions.yml` now runs the Python test suite before generating,
  uses `fetch-depth: 0`, targets `${GITHUB_REF_NAME}` instead of a literal
  `main`, retries the push with a rebase abort on conflict, and opens or updates
  a deduplicated issue labelled `pipeline-failure` on failure. A successful run
  closes it. Concurrency now queues rather than cancels, because a cancelled run
  reports `cancelled` rather than `failed`.
- `deploy.yml` runs the frontend tests before building, caches npm, declares the
  `github-pages` environment so the deployment URL is reported, and passes
  `VITE_DATA_BASE_URL`.
- `audit.yml` runs daily after generation and asserts the site responds, its
  assets resolve, the published JSON parses, and the data is at most three days
  old. A failure opens an issue labelled `site-audit`.

### Frontend

- The runtime data base URL is read from `VITE_DATA_BASE_URL`, falling back to
  the previous hard-coded location.
- `results.json` is now optional. It supplies only a subtitle and footer
  attribution, but previously a failure there blanked the entire dashboard.
- A staleness banner appears when `data_freshness.stale` is set, with a fallback
  computed from `model_state_as_of_date` so legacy payloads are also covered.
- An error boundary renders a message instead of a blank page when a payload is
  malformed.
- `frontend/public/data/*.json` is no longer tracked. Only `predictions.json` was
  ignored previously, so `results.json` was committed and permanently stale
  because the bot never staged it. `npm run sync-data` copies the current
  artifacts for local development.

### Documentation

- Root `README.md` gained status badges and how-to-run / how-to-deploy sections.
- `.github/workflows/README.md` describes the test gate, alerting, retention,
  and audit job, and no longer claims that retries protect against a stale
  snapshot.

were reachable. This is the intended split: availability and recency are
reported separately.

## Residual risks

1. **Unpinned dependencies.** `requirements.txt` has no versions and there is no
   lockfile, so a dependency release can change numerical results between runs.
2. **Polymarket coverage is external and intermittent.** On 18 October 2026 the
   API returned only ATP and ITF events, so zero WTA fixtures matched and the
   market comparison was hidden. This is upstream coverage, not a defect, and
   the UI degrades silently by design.
3. **Hard-coded defaults remain.** `VITE_DATA_BASE_URL` falls back to
   `ryantjx/tennis_ssm/main`; a repository rename still requires setting the
   repository variable.
4. **Scraping is inherently fragile.** Link discovery reduces the blast radius of
   URL changes but cannot protect against an HTML restructure. The audit job's
   three-day recency window is the backstop.
5. **Staleness never blocks publication.** This is deliberate, but it means a
   persistently failing run leaves the site serving old data until the issue is
   acted on. The issue-based alert is the mitigation.
